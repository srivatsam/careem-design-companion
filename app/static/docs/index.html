01 Overview

Atelier Noor is a shopping advisor for perfume. A shopper describes what they like in their own words, or answers a short guided interview, and the advisor replies with three perfumes it has actually looked up in the catalogue, a reason for each, and one suggestion for what to layer with the first pick. Everything runs on one FastAPI service and one self-contained JavaScript file.

  • Free-text chat in English or Arabic, answering in whichever language the shopper writes.
  • Guided match: an adaptive interview of at most five questions with tappable answers, which the shopper can end early at any point.
  • Three picks and a layering idea per recommendation, each pick a real catalogue row with its notes, family, strength and price.
  • Refine chips after every set of picks: less sweet, fresher, cheaper, stronger, lighter, or more like one of the picks.
  • Wishlist that only saves after the shopper answers yes to a direct question naming the perfumes.
  • Two ways to run: a full-page advisor, or a floating launcher embedded on any page with one script tag.

03 Infrastructure and deployment

The live site runs on Azure App Service as a Linux container, one always-on instance in UAE North. The container image is built in an Azure Container Registry, so no local Docker is needed. The SQLite file lives on an Azure Files share mounted at /data, which survives restarts and redeployments. Application output goes to App Service container logs. The Bicep templates under infra/ describe an alternative deployment on Azure Container Apps that shares the same image and the same file-share approach.

A release is a container build in the registry under a fresh image tag, then repointing the app at that tag, which restarts it. The previous tag stays pullable, so rolling back means redeploying the earlier tag. Data written since is not rolled back with it.

Start-up. The entrypoint counts the perfumes already in the database. On an empty database it imports the bundled seed catalogue and any CSV baked into the image, builds that on container-local disk and moves the finished file into place in one step, so a restart mid-import simply re-runs the import next boot. When rows already exist, the import is skipped and the server starts straight away. GET /api/health reports the perfume count, model and embedding status and any brand filter, and backs the container health check.

05 How the agent works

  1. Message. The page posts the shopper's text and session id to /api/chat.
  2. Safety and scope checks. Regex gates for prompt injection, medical or allergy questions, an active brand filter, and off-topic requests run first. Any match returns a declined reply with no model call. A pending wishlist consent question is answered here too.
  3. Taste profile. The session row is read from SQLite and the stored taste profile is merged with anything the message itself reveals, so every later step works from one picture of the shopper.
  4. Agent with tools. The agent runs one turn against Azure OpenAI with five tools: search_perfumes, get_perfume, find_similar, suggest_layering and save_wishlist. The prompt forbids naming any perfume a tool has not returned in this turn.
  5. Grounding check. An output guardrail compares every recommended and layered perfume id against the ids tools actually returned. Anything else is dropped.
  6. Server post-processing. Hard constraints are re-applied over the model's picks, brand and line duplicates are swapped out, and the written reply is reconciled with the cards so it never names a perfume that is not shown.
  7. Response. One JSON object carries the reply text, up to three perfume cards, a layering suggestion, refine chips, the next question, and the updated profile.

Guided match

The first question, “who is this for?”, is served instantly with no model call. After that the model writes each question itself, with two to six tappable answers, and each answer is read against the question that was asked. The server tracks which topics have been covered so a question is never repeated, and holds recommendations back until the shopper has answered at least two questions beyond the first and given at least two real taste signals. Recipient or gender alone never counts. Five questions is the cap, and the shopper can ask for picks at any point through /api/guide/finish.

Grounding and safety

Only perfumes returned by a tool in the current turn can be recommended; the guardrail drops the rest, and a total grounding failure falls back to the deterministic recommender rather than an empty answer. The wishlist tool checks a server-side consent flag instead of trusting the model, so a save happens only after an explicit yes. Medical, allergy and off-topic requests are declined with a short explanation, prompt-injection attempts are refused, and all user text and tool output is treated as data. Requests are limited to 30 per minute per IP address. When the model errors or times out, the rule-based extractor and recommender answer instead.

06 Recommendation engine

The catalogue is loaded into an in-memory index at start-up and scored deterministically. The engine works on its own, with no model in the loop, which is what the fallback path uses.

SignalWeightWhat it measures
Note and accord match0.50Cosine similarity between a profile vector (liked notes ×2, requested families ×2, mood hints ×0.5, anchor perfume ×3, avoided families −1.5) and each perfume's note/accord vector.
Semantic match0.30Embedding similarity when an embedding deployment is configured; otherwise an IDF-weighted keyword overlap expanded through the note and family taxonomy.
Quality signal0.20Shrunk rating blended with popularity, clamped to 0–1.
Strength and season fit×0.7 + 0.3 × fitMultiplier applied to the weighted total, from how close the strength is and whether seasons and occasions overlap.

Hard filters

A perfume is discarded outright, before scoring matters, when it is marked not recommendable, is the anchor perfume or a flanker of the same line, falls outside an active brand filter, is priced above the stated budget, carries a disliked note, sits in an avoided family, is more than two steps from the requested strength, or does not match a stated gender.

Variety rules

  • At most one perfume per brand among the three picks.
  • Near-duplicate line extensions sharing a leading name are skipped.
  • The three picks never all share one family, unless the shopper asked for exactly one family and named no notes.
  • The anchor perfume and its flankers are excluded on every path, so “something like X” never returns X.
  • When too few candidates remain to fill three picks, brand and line variety is relaxed and the next best matches fill the gap.

Semantic matching

Embedding-based scoring is implemented and switched off in the live deployment: no embedding deployment is configured, so the semantic term falls back to the keyword and IDF path.

07 Data model

One SQLite file holds both halves of the system: catalogue tables written by the importer, and session tables written as shoppers use the advisor.

Solid lines are foreign keys; the dashed line marks the perfume ids a wishlist or feedback row refers to.

What a session stores. Sessions are anonymous: a random id, no account, no sign-in, no cross-session identity. Each row holds the language, the taste profile and guided state as JSON, the perfume ids last shown, a wishlist consent flag, and the conversation history capped at the last 30 turns. The agent is given the last 12 turns of that history on any one call.

Taste profile fields. liked_notes, disliked_notes, families, avoid_families, moods, occasions, seasons, strength (1–5), budget_aed, anchor_perfume, anchor_perfume_id, anchor_cheaper, brand, gender, guided_for and free_text. Every field is optional, and two profiles merge by union for lists and last-value-wins for scalars.

09 Embedding the widget

Floating launcher, the default, on any page:

<script src="https://<host>/widget.js" data-lang="en" data-brand=""></script>

Full-page mode, mounted into an element, which is how the advisor homepage uses it:

<main id="agent"></main>
<script>
  var s = document.createElement('script');
  s.src = '/widget.js';
  s.setAttribute('data-lang', 'en');
  s.setAttribute('data-mode', 'page');
  s.setAttribute('data-mount', '#agent');
  document.body.appendChild(s);
</script>

data-lang sets the starting language, en or ar. data-brand is sent when the session starts. data-api points at a different API origin, defaulting to the origin that served the script. data-mode="page" switches from the floating launcher to inline full-page mode, and data-mount is the CSS selector of the element it mounts inside.

10 Quality and performance

170 unit and API test functions cover the recommendation engine, the guided flow end to end, the agent tools and grounding guardrail, rule-based extraction in both languages, card and price localisation, image generation, and the HTTP surface including the safety gates.
